# cpu1c launch attempt 2: chain started, stopped at its own prerequisite stage (checker defect; nothing native ran)

Attempt 2 used `cpu1c-launch-wrapper2.sh` (sha256 `6464aa4c5969bdb04d4f0dd9d6be3706c1e32f7f770f0408b33370e1bf9da989`, real default environment, fresh exclusive marker `logs/cpu1c-launch2`, outer CPU lease `/tmp/motioncorr-c1-cpu8-9.lock`).
Receipts (22 Oct 2026, UTC): wrapper pid 3308367, uid 1004, argv `…/cpu1c-launch-wrapper2.sh`, mask 8-9, lease acquired 22:21:27Z, gate created 22:21:29Z; chain pid 3308375 started 22:21:37Z with mask 8-9 (`chain.cpus.copy`).
The first stage `cpu1c-prereq` ran 22:21:37Z and exited **1**; the chain wrote `logs/chain-cpu1c.stop` ("stage cpu1c-prereq exited 1 (allowed: 0)"), the wrapper exited 1 and released the lease. No other stage started and no native program ran.

Cause: 24 of the 25 prerequisite checks passed (including the affinity 8-9, the deployed-tool manifest, the F-cpu run pins, source, binaries, identities); the failing check was `fresh_stage_names`. It lists `logs/cpu1c-*` entries other than `cpu1c-prereq.*` as stale stage names, and it counted the operator's launch-marker directories (`cpu1c-launch` from attempt 1 and `cpu1c-launch2`). The frozen design placed the launch marker under the same `cpu1c-` prefix as the stage names, so any launch marker would have tripped it; it is a defect in the prerequisite/launch naming, not a result about C1, the CPU binary, or any fixture. Attempt 1 (`../launch-attempt-1`) and this attempt are retained unchanged.
Consequence: stage names `cpu1c-*` are now reserved (exclusive), so the same chain cannot be run again. A new launch needs a new, frozen prefix (proposal: `cpu1d`) with the check fixed to ignore launch markers (or markers moved outside `logs/cpu1d-*`) and unchanged stage content. No retry was made.
