## Fixes (each with the tests that must fail on the old code)

- **F1 leases through sealing.** `finish()` stops releasing the leases. `execute()` releases them in a final `finally`, after the child group is reaped, after the records, the release copy and the manifest are written, and also when any of that raises. Tests: with real file descriptors, another descriptor cannot acquire any of the three locks while `pair_report` and `write_manifest` run (normal stop, ordinary stop, and an exception raised inside `write_manifest`), and can acquire all three only after `execute()` returns. The manifest never hashes a live file and never lists itself (existing rule, re-asserted).
- **F2 per-job inputs against the frozen pins.** Before every producer the driver re-hashes `MANIFEST.json` against the pinned manifest hash and every file of the fixture tag the job uses (K267 33, N 26: inputs and truth) against the pinned `file_hashes`, and the staged `.star` and `.mrcs` copies against those pins; the mutable manifest is no longer a reference. The pins are never regenerated during a native run. Tests: input and manifest tampered together (so they agree with each other), truth file tampered, manifest alone tampered, an N job: each stops before the child starts (no `stdout.txt`, no receipt). A revert-mutant that compares with the manifest again must fail the together-tamper test.
- **F3 guard bytes.** Before every guard call the driver reads the guard file, hashes those bytes against the pin and runs exactly those bytes (`bash -c <verified text> guard LABEL NEED_GPU`), so a replacement after the check cannot execute. In a real run the pinned tool modules and the guard are also re-hashed before every job. Tests: a sentinel script put in place of the guard after `verify()` stops the campaign before it runs (marker file absent, the process spawn never reached); the unmodified guard is invoked with the pinned text; a changed module pin stops a real-mode driver. No new tolerance.
- **F4 release record.** The exact release bytes are copied into the run directory (`release_copy.json`, under the leases), and `final_status.json` carries the release sha256, `run_id` and `authorized_by`; the copy is in the manifest. The driver never creates a release. Test: a real-mode driver (no producer) records and seals a copy with matching hash and fields.
- **F5 guard hook predicate.** `env | grep -q` under `pipefail` (SIGPIPE on a large environment) is replaced by a builtin that needs no pipe (`compgen -A variable STAGEC_TEST_`). Tests: several large `STAGEC_TEST_*` environments (placed so that a match precedes the bulk, each variable under the Linux per-variable limit) and a small one are rejected with code 20 when `STAGEC_REAL=1` and without test mode; the old predicate (checked once on a scratch copy and recorded) was bypassed by the large case. The production driver still refuses `STAGEC_TEST_*` itself.
- **F6 what the argv/env check is.** Documented here and in the driver: the "executed command or environment differs" check compares what the spawner passed with the ledger-derived command; it is a spawner record, not independent proof from the OS. New records: the complete child environment actually passed (PATH, HOME, LANG, LC_*, TMPDIR, USER, LOGNAME as allowlisted; everything else, including `LD_LIBRARY_PATH` and `LD_PRELOAD`, dropped, and the dropped names) in every receipt, and on Linux the first sample's `/proc/<pid>/cmdline`, `exe` and `environ` digest and keys (recorded, not a new stop). Stage B and the retained producer calls used the full inherited environment; Stage C scrubs it, and equal library resolution is not asserted: it is UNRUN. Prepared only: `tools/stageC_ldd_preflight.sh`, which the parent runs with the resource grant (not run here, no SSH, no CUDA, no native job), prints `ldd` of the three binaries and the two oracles under the exact scrub environment and under the full environment, with the sha256 of each resolved library and a match or differ verdict. Existing metadata does not contain loader resolutions; that gap stays listed. `gpu_status: OBSERVED` is documented as "a tree pid was listed", not "on GPU2".
- **F7 manifest self-listing.** The original `evidence/stageC/amend1_window/SHA256SUMS` lists itself (re-checked: 12 lines OK, 1 FAILED `./SHA256SUMS`) and is left untouched. A dated amendment and a closed `SHA256SUMS.v2` (every file except itself and the amendment) are added; every new manifest written by this work excludes itself and every live writer. A test records the actual counts.
